ssh-snakehole specification / 9. Validation and delivery

Evidence before a security claim

A new SSH/crypto implementation is considerably more work than composing mature native libraries. Do not estimate it as a short wrapper sprint. The scope is a focused desktop SSH library, not a complete replacement for every upstream project's features. Build one working vertical path, prove its protocol behavior and limits, then expand only the used feature set.

Use unittest and standard test helpers where sufficient. A development-only native reference implementation and fuzzing tools are permitted. Tests must prove observable behavior and attack handling, not mirror internal function bodies. Preserve regression fixtures for genuine protocol/security failures. Avoid repeated broad testing without a new failure or change.

Platform evidence

CI exercises CPython 3.12, 3.13 and 3.14 on Windows x64, Linux x64 and macOS Apple silicon, plus real ARM64 Windows/Linux and Intel macOS evidence before claiming those targets. Emulation is useful but does not prove native OS filesystem/process behavior. Mark an untested cell unsupported rather than implying the source-only wheel proves it works.

Test default loops and a rejected Windows Selector loop, Unicode home paths, spaces/quotes in installation paths, user/admin-intent contexts, TLS trust setup and process cleanup. A WSL test proves Linux behavior in WSL, not native Windows behavior. Remote commands run only on authorized test hosts; previous permission to use a sibling computer is not a substitute for a controlled destructive-test environment.

Cross-platform network pairing must include Windows-to-Linux, Windows-to-macOS and Linux-to-macOS. Reverse each host/operator role for exec/path/privilege differences. Two clients on one machine do not prove NAT behavior. Use computers on separate NATs or controlled VM networks, disable direct hints, and verify that both originate outbound relay connections with no router/firewall changes.

Measured performance gates

These are proposed minimum usability targets, not benchmark claims: warm local import under 250 ms; local pairing+SSH crypto work under two seconds excluding network/user delay; sustained single-stream file payload at least 1 MiB/s on a defined modern laptop per supported architecture; idle CPU under 1% of one core; and no event-loop stall over 100 ms during a bulk transfer. Report hardware, Python version, payload, cipher implementation, measurements and variance.

Network queues must remain within their declared budgets while transferring 2 GiB and while a consumer stalls. Record process RSS separately because interpreter overhead, capture buffers and worker memory are outside network credit counts. Define a measured RSS budget once the first vertical implementation exists; do not invent one before choosing crypto structures. Capture-limit failure must stop memory growth even when remote output continues.

If pure Python bulk encryption misses the target, first measure and simplify. Bounded algorithmic improvement is allowed; adding a compiled accelerator violates this product's requirement. If it still cannot serve software-installation workloads, publish the measured limitation and revisit scope before calling it a full replacement.

Decisions before a production release

  1. Audit selected pure Python dependency versions and all translated files, including licenses. No unchecked optional native paths; ctypes is limited to reviewed built-in OS APIs.
  2. Accept or revise the threat model for nonconstant-time Python crypto. Resolve every critical/high correctness finding before release.
  3. Demonstrate repeated Transit relay pairing and actual internet reachability. Choose public relay use with permission/capacity or deploy an owned service, including a tested 443 path if it is promised.
  4. Prove Windows token/DACL/job ownership and Unix pipe-watcher lifecycle, publish macOS/POSIX validation and detachment limits, and accept the protected manual-admin launch policy. Do not market universal rollback or descendant containment.
  5. Meet or explicitly revise performance targets with measurements. Publish supported platform cells truthfully.
  6. Publish real, tested bootstrap/release URLs only after implementation. Offline artifacts include all source-only imports and notices.

What was validated during this specification task

The baseline source and upstream manifests/protocol sources were inspected, and source revisions were recorded. The authored HTML set is checked for local links, anchors and traceability. No crypto implementation, protocol interoperability, platform behavior, security review or performance result is claimed by this document. Those remain the implementation's acceptance work.
