ssh-snakehole specification / 3. Pairing and transport

The code opens a session, not a public SSH port

Connection sequence

  1. The host passes readiness checks, creates a fresh Ed25519 host key, session ID and Transit secret, then reserves a Wormhole nameplate.
  2. The host prints a code such as 42-orchid-lantern-copper-sparrow. This is an illustrative shape, not a live code or a promised word-list combination.
  3. The operator opens the same mailbox using that code. Both sides complete compatible symmetric SPAKE2 and authenticated version exchange.
  4. The host sends its public SSH key, expiry and transport offer through encrypted application messages. The operator creates a private Ed25519 key locally and returns its public key, bound to this offer.
  5. The host authorizes that one key, sends an acceptance, and both sides close the mailbox. The nameplate/code is consumed.
  6. The computers connect outward to a Transit relay, validate opposite-role ready messages and start a real SSH handshake. The operator verifies the exact PAKE-pinned host key; the host verifies the authorized operator signature.
  7. SSH channels carry commands and SFTP. Closing the host revokes the entire invitation and closes every transport, channel and listener.

The relay joins two outbound sockets. This is why router port forwarding is unnecessary. It still requires reachable relay infrastructure and allowed outbound traffic. The mailbox service carries only pairing/control material. The Transit service carries the ongoing encrypted SSH traffic. They can run on different servers.

Mailbox and PAKE compatibility

Use AppID io.github.heetbeet.ssh-snakehole/v1, encoded as UTF-8, for both the mailbox binding and SPAKE2 symmetric identity. The full canonical code, including numeric nameplate and all four words, is the password byte string. Allocate four words using the audited upstream position-dependent word-list data and cryptographically secure entropy. Do not invent syllables or use Python's random.

The normative wire behavior is the pinned mailbox protocol and client protocol. Preserve message encodings, symmetric SPAKE2 group parameters and phase-key derivation exactly. Interoperate with a reference Wormhole client using this AppID and application schema; do not claim compatibility with the upstream file-transfer app.

A research discrepancy must be resolved deliberately: the mailbox protocol document describes binary WebSocket JSON messages, while the pinned Python reference sends and asserts text frames. The default client sends UTF-8 text JSON to match that implementation and accepts either correctly encoded text or binary JSON on receive. Its relay module accepts both. Transit WebSocket payloads remain binary only. Test this distinction against a real reference mailbox rather than applying one framing policy to both services.

The implementation must track welcome, bind, allocate/claim, open, add, release and close outcomes separately from acknowledgements. Ignore unknown upstream fields as that protocol requires. Conversely, our encrypted application records below reject unknown fields. Deduplicate exact repeated phase bodies, reject a different body for an already seen peer phase, and reorder numeric phases within a bounded gap. A third peer, wrong password, reflected SPAKE message or bad authenticated version is a terminal pairing failure. Never reuse that code after such a failure.

Code input strips surrounding whitespace and allows ASCII case normalization for words. It rejects internal whitespace, extra components, non-ASCII lookalikes, path-like inputs and codes exceeding 256 bytes. Numeric nameplates are decimal strings without numeric conversion that could overflow. The generated code uses the exact upstream vocabulary; the example above only demonstrates readability. An optional verifier comparison is exposed through the library for applications that need a human confirmation step.

Application phases

Encrypted phaseSenderRecord
0Hostoffer, defined below
0Operatoraccept containing schema, session_id, SHA-256 of the exact offer bytes, and client_key
1Hostready containing schema, session_id and SHA-256 of the exact accept bytes

Phase numbers are per sender. Operator phase 0 is sent only after receiving the host's offer. Host phase 1 is sent only after validating the operator key and allocating its authorization slot. Upstream encrypted version app_versions declares {"ssh-snakehole": 1}; reject a peer missing the application version or declaring a conflicting role. Our offer carries role host, accept carries operator, ready carries host. Binding role, exact bytes, session ID and version prevents using an offer in a different exchange.

Offer and ticket contract

{
  "schema": "ssh-snakehole/1", "type": "offer", "role": "host",
  "session_id": "32 lower-case hex characters",
  "host_key": "ssh-ed25519 BASE64_OF_SSH_KEY_BLOB",
  "transit_key": "BASE64_OF_32_RANDOM_BYTES",
  "host_side": "16 lower-case hex characters",
  "operator_side": "different 16 lower-case hex characters",
  "relay": "tcp:transit.magic-wormhole.io:4001",
  "direct": [],
  "host_os": "windows | linux | macos", "host_name": "display label",
  "process_user": "display label", "privilege": "user | admin | unknown",
  "expires_at": "UTC RFC3339 timestamp with Z and whole seconds"
}

Required fields are exactly those shown. A direct hint is an object with host as a numeric IP address and port as an integer from 1 to 65535. At most four hints are allowed. The complete offer and each other application record MUST be at most 8192 UTF-8 bytes. JSON parsing rejects duplicate keys, NaN/infinity, trailing bytes and invalid types, including booleans where integers are expected. Base64 is strict, without ignored characters. Display labels are at most 256 bytes each and are never used in a command or path.

The operator's accept contains one ssh-ed25519 public key in the same key-blob encoding. The host rejects extra authorized keys and stores no operator private material. Tickets combine the accepted offer, locally generated 32-byte operator seed, offer/accept hashes and the code fingerprint. Tickets are capabilities. repr, exceptions and status output redact their secrets. Ticket expiry cannot exceed two hours plus a one-minute clock-skew allowance when first received; each side still enforces the earlier local deadline.

Session ID is 16 random bytes. Transit key is independent 32-byte entropy, sent only over PAKE-authenticated encryption. Side IDs are independent eight-byte random values, distinct within the invitation. Derivations use the pinned Transit HKDF labels, with stdlib HMAC-SHA256 implementing RFC 5869. Do not derive the Transit secret from the human code or public session ID.

Transit stream profile

The pinned Transit specification permits a raw bidirectional stream for protocols such as SSH. Use that mode. It avoids a second bulk encryption layer while SSH supplies fresh key exchange and authenticated packets. XSalsa20-Poly1305 remains required for Wormhole's small pairing messages.

Assign host the Transit Sender/Leader role and operator Receiver/Follower. The role names do not constrain the direction of SSH traffic. Use the standard sided relay handshake and standard role-ready derivations, then the Sender's go\n. Their exact strings and HKDF context labels are normative from the pinned Transit document and reference implementation. Note the actual relay syntax includes for side; do not infer a wire grammar from informal summaries.

Before go, accept only the exact expected handshake and bounded line lengths. Cap relay greeting at 128 bytes, role-ready line at 256 bytes and all accumulated pre-SSH bytes at 1024. Timeout each transport candidate at ten seconds, with a 40-second total dial budget. After go, pass remaining buffered bytes directly into SSH. Do not lose coalesced SSH banner bytes or assume a read returns one message.

The host's pending relay registration is an exception to the operator's ten-second candidate timer: it waits up to 270 seconds for a partner, then refreshes before a five-minute server timeout. Send only the relay registration line while waiting. The reference relay emits ok\n only when a partner arrives and rejects early payload as impatient. Start the host's ten-second role-ready/SSH pre-auth deadlines after that match, not while waiting for someone to reconnect. This prevents idle reconnect support becoming a ten-second relay churn loop.

Default deployment uses tcp:transit.magic-wormhole.io:4001, the upstream configured endpoint. That is evidence of the configured service, not a service-level agreement or a promise it is reachable from every network. Production launch requires approval of relay use/capacity or a project-owned deployment. Never claim public WSS-on-443 availability without testing an actual endpoint.

A configured wss:// Transit relay can be used through the same audited WebSocket adapter. Binary message payloads are concatenated into a byte stream regardless of fragmentation. Compression is disabled. HTTP proxy support is not in v1; blocked outbound paths produce a useful error. No fallback disables mailbox TLS validation or SSH identity verification.

Optional direct connection

Default mode opens no incoming network listener. A host may explicitly supply numeric local bind addresses to enable direct TCP. It owns one ephemeral listener per selected address, authenticates the Transit handshake before SSH, and includes reachable hints in the encrypted offer. No interface enumeration, external IP guessing, TCP STUN, UPnP, NAT-PMP or firewall-rule changes occur automatically.

Operator tries validated direct hints immediately and starts the configured relay after 500 milliseconds. The host chooses the first valid candidate and closes losing candidates for that connection. A hint cannot change the configured relay or add arbitrary DNS names. Reject loopback, multicast, unspecified and link-local destinations from peer hints, including metadata-service addresses. Private unicast addresses are accepted only with explicit direct mode because LAN access is its purpose. This validation limits misuse; an authorized malicious operator already has account-level execution after SSH authentication.

Reconnect after the mailbox closes

The ticket retains the Transit key, fixed role side IDs and relay address for the lifetime of that host. Host maintains one pending outbound relay connection. Once paired with an operator connection it transfers that stream to SSH, then starts another pending relay connection. Active streams are independent; at most eight authenticated SSH connections and sixteen total incomplete handshakes may exist. There is no need to retain or reopen the Wormhole mailbox.

The reference relay removes matched requests from its pending map and groups pending connections by token and side. Reusing the invitation's token permits new matches while earlier sockets remain active. Fixed same-role side IDs prevent two host pending sockets matching one another. This application use of repeated Transit matches MUST pass an integration test against the pinned relay before being relied upon.

The stable relay token is visible to the relay and allows traffic correlation and denial of service. It is not an SSH credential. Transit ready messages can be replayed by an observer of that handshake; only fresh SSH key exchange, pinned host identity and operator signatures authorize access. Do not authenticate a command based on Transit success. Fresh SSH ephemeral keys are generated for every connection and rekey.

A reconnect creates a new SSH connection with the same pinned host and authorized operator key. It never restarts an interrupted command, resumes a partial upload silently or creates a new host after expiry. If a stream fails after execution began, report OutcomeUnknown unless an exit status was already confirmed. Host restart always creates a new invitation and keys, even if hostname and cache directory are unchanged.

Relay operational specification

The client library may interoperate with established public mailbox and Transit servers. These external servers are explicit services, not locally imported dependencies. A self-contained Python deployment is also specified: port the used mailbox allocation/claim/add/release/close subset and Transit TCP/WSS forwarding state into a separate relay module, using asyncio, wsproto/h11 and sqlite3. It is not required to run for ordinary client import.

Mailbox persistence holds opaque bodies and phase IDs, scopes all operations by AppID, distinguishes nameplates from random mailbox IDs, and preserves upstream two-party semantics. Limit messages to 64 KiB, 256 messages per mailbox, 1 MiB queued per mailbox and two claimed sides. Close/release must be idempotent. Unclaimed nameplates and abandoned mailboxes expire after a configurable operator retention window, default one hour. Retention must not terminate a valid ten-minute pairing unexpectedly.

Transit relay never parses SSH. It matches standard token/side handshakes, forwards bytes with bounded queues of 256 KiB per direction and closes both sockets when one disconnects. Pending connections expire after five minutes; the host refreshes its pending socket before that deadline. Per-IP and global connection/bandwidth caps protect capacity but do not establish identity. Rate limits and capacity are deployment settings, not client negotiation fields.

WSS service uses stdlib ssl with a deployment-provided certificate/key, or an explicitly external TLS terminator operated by the relay owner. No ACME client, DNS server, TURN server, reverse proxy binary or certificate issuer is silently bundled. Self-host documentation must separate required external infrastructure from Python package purity. Relay logs omit full tokens, codes and mailbox bodies and publish retention policies. Public relay load tests require owner authorization.
